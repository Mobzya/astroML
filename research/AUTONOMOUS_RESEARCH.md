## Порядок каждой сессии

1. Работать в этом чате и последовательно. Не создавать другие чаты, субагентов и параллельные исследования. Если предыдущая итерация ещё выполняется, не запускать вторую.
2. Источник состояния — GitHub. Найти действительный checkout по remote `Mobzya/astroML`; при отсутствии локальной папки восстановить checkout из GitHub. Не предполагать, что `/workspace` или `.venv` сохранились. Если доступны только инструменты GitHub, продолжать чтение/документирование, а вычисления честно отметить BLOCKED.
3. Прочитать `AGENTS.md`, `research/STATUS.md`, `research/task_queue.json`, `research/decision_log.md`, настоящий файл и нужные проектные навыки. Проверить remote, HEAD и рабочее дерево. Не перезаписывать изменения пользователя и не делать force push.
4. Выбирать первую обычную задачу активной кампании с выполненными зависимостями (порядок в JSON). Завершение старого baseline не останавливает новую неделю. `campaign_finalization` нельзя брать просто потому, что её setup dependency выполнена: применяются trigger/finalization_start правила. До финального окна продолжать активную незавершённую задачу; BLOCKED позволяет последовательно взять независимую ready-задачу (например data audit). На последнем окне сначала обеспечить final handoff; не начинать новый длинный fit. Взять первую задачу с выполненными зависимостями. Незавершённую IN_PROGRESS продолжить прежде новой. Перед началом записать точную подзадачу, ожидаемые артефакты, границу проверки и следующий checkpoint, закоммитить и отправить в GitHub.
5. Планировать примерно **120 минут активной исследовательской работы** за сессию. Выполнять последовательность конкретных задач из очереди: первоисточники, математические проверки, дизайн и проверяемые эксперименты. После завершения небольшой задачи и сохранения результата переходить к следующей готовой по зависимостям, если остаются время и доступные ресурсы. Одновременно выполнять только одну задачу. Не подменять исследование переписыванием плана. Незавершённую задачу сохранять как IN_PROGRESS с точным checkpoint, не объявлять её DONE.
6. Сохранять промежуточные результаты после существенных подзадач. Каждые ~20 минут активной работы стремиться фиксировать доступный checkpoint; это рабочее правило, не гарантия сохранения при внезапном прерывании. Не начинать длинный неделимый запуск в конце сессии.
7. Обновить task_queue, STATUS и датированный отчёт: что прочитано/сделано, точные ссылки или команды, SHA кода, результаты/CI, что не доказано, препятствие и следующий минимальный шаг. Перед отправкой проверить ссылки/форматы и соответствующие коду тесты, если код менялся. После успешного push проверить remote SHA.
8. Ответить кратко по-русски в текущем чате: результат, ссылки на GitHub, ограничения и следующая задача. Личные объяснения ученика не считать выполненными за него.

## Ограничения ресурсов и научной корректности

- Лимиты аккаунта и время их сброса агенту не видны. Интервал 8 часов не гарантирует доступность по недельному лимиту. При quota/network/auth ошибке сохранять то, что возможно; не покупать resets, credits, GPU и API-вычисления. Следующий доступный запуск продолжает checkpoint.
- Целевой бюджет сессии — **около двух часов активной работы**, а интервал между началами запусков остаётся **8 часов**. Это ориентир планирования, а не гарантия длительности платформенного запуска. Завершение одной маленькой подзадачи само по себе не заканчивает сессию: последовательно продолжать очередь. Не продлевать работу пустым ожиданием и не повторять уже успешные проверки ради времени; досрочно завершать при полном завершении цели, исчерпании доступного запуска или блокировке всех полезных задач, сохранив состояние. CPU development pilot по-прежнему ≤50 независимых источников и ≤15 минут; до 4 workers с одним BLAS thread после измерения памяти. Длинный опыт разбивать на возобновляемые batches и заранее оценивать бюджет.
- Нельзя менять критерии по evaluation, открывать reserved final test для разработки или подавать truth в inference. Все виды одной latent pair — одна кластерная единица.
- Литературу отмечать как abstract/sections/full text только по реально прочитанному. Сохранять DOI/URL, версию, конкретные страницы и границы вывода; доступные чужие полные тексты не перепубликовывать автоматически.
- Новый namespace и зафиксированный протокол до основной evaluation. Oracle covariance отдельно от практического метода. Все seeds, failures, отрицательные и неопределённые результаты сохраняются.
- Большие артефакты хранить в GitHub Releases при доступе, с SHA256/manifest и загрузчиком; компактные отчёты/данные — в Git. Нельзя удалять единственную локальную копию до подтверждённой загрузки. Если постоянное хранилище недоступно, не запускать опыт с невосстановимыми результатами.
- Интерфейс, CV и сложные нейросети отложены до законченного основного результата. Математическая/статистическая честность первична.

## Session lease и защита от второго запуска

Перед научной работой проверить процессы предыдущего runner (в текущем workspace при наличии) и `research/session_state.json`; tool run history по возможности сверить с timestamp. `in_progress` сам по себе не доказывает liveness, null не доказывает отсутствие запуска. Не печатать credentials и не публиковать private thread/automation IDs.

Если есть свежая lease другого owner или известный живой fitting process — не начинать второй. Сохранить доступное объяснение и выйти из этой итерации без изменения чужой lease. Если lease истекла, проверить liveness/сервис/сохранённые checkpoints; истечение не является доказательством смерти процесса. Необъяснимая неопределённость — `BLOCKED_SESSION_LIVENESS`, уведомление и checkpoint, не параллельный fit.

Если предшественник завершён/lease свободна, создать unique owner_id, task_id, started_utc,last_checkpoint_utc,expires_utc (ориентир3часа), по возможности PID+process_start. Сначала commit и успешный обычный push lease/task checkpoint, потом работа. Push rejection требует fetch/повторной проверки ownership, не force/не слепого merge чужого owner. Перед каждым batch сверять владение/срок; не продолжать потерянную lease. Heartbeat примерно20мин, на окончании очистить active_session/status=IDLE, сохранив незавершённый task checkpoint. Этот Git lease снижает риск дубликата, но не объявляется гарантией liveness платформы.

## Завершение и остановка

Baseline R2/COV05 уже завершён и передан; историческая очередь остаётся DONE. **Новая кампания** заканчивается через W1-HANDOFF, когда все её обычные задачи реально завершены, либо все доступные полезные задачи действительно блокированы, либо наступило финальное окно09.11 19:15UTC/срок09.11 21:15UTC. Не завершать новую неделю после первого малого опыта/старой рукописи; не продолжать бесконечно новые необъявленные исследования.

В финальном окне приоритет — save/restore evidence, честный completed/pending/blocked список и точный следующий минимальный шаг. Невыполненные задачи не маркировать DONE. COUNT21 ограничивает будущие старты; сервис не гарантирует выполнение каждого окна. После успешного handoff push уведомить пользователя и приостановить только своё AstroML задание, не другие автоматизации. При недоступном pause API сохранить фактическую блокировку; не выдавать намерение за подтверждение.
